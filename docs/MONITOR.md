# Signal Monitor — メッセージ本文のリアルタイム変換

元のSignal Monitorの波形・A/Bのメッセージ欄を基準にしています。独立の変換パネルではなく、本文の末尾が `N → NA → な` と同じ位置で変化します。ローマ字とかなは同じ文字サイズです。A/Bの欄には、それぞれの最後の発言を表示します。

次の返答を生成・待機する際は古い本文を待機表示へ切り替え、過去の文章は履歴に残します。ACKも「受信しました」（英語はRECEIVED）を実際にモールス本文として送り、受信文字から独立したメッセージへ復元します。ACK本文は次のLLM入力には渡さず、推論要約も送信しません。

## 起動

Python 3.10以降、`websockets==16.0`、Node.js 20以降が必要です。LM Studioで `gemma-4-e2b-it` を読み込み、OpenAI互換サーバーを `127.0.0.1:1234` で起動してから実行します。

```powershell
Start-Monitor.cmd --port 18790
```

画面は `http://127.0.0.1:18790/`。話題、日本語／English、速度を入力し「会話をはじめる」を押します。既定は60 WPM（短点20 ms）、停止ボタンを押すまで継続します。タブの切断・通信や生成の失敗でも停止します。4／6ターンの有限実行は検証API用に残しています。サーバー／モデルが使えない場合はエラーを表示し、台本へ切り替えません。

「音を確認」は会話を始めず短い確認音を鳴らします。音声を有効にした閲覧画面でも、別の所有画面が開始したライブ信号を再生できます。音量とミュート状態は保存し、履歴の再読込では音を鳴らしません。「音あり」は実際にAudioContextが動作し、出力が有効な場合だけ表示します。

モデルの設定は `E2B_URL` と `E2B_MODEL`。会話の接続先はループバック限定です。新規会話の開始は同一Originの画面だけに許可し、同時に1セッションのみ所有します。

入力したトピックは発言として送信しません。セッション開始時にA/Bの両ワーカーへ同じ「話題データ」として渡します。両者が話題と自分の役割を確認した後、Aだけが話題に沿った最初の発言を生成し、Bはそのモールス受信を待ちます。2ターン目以降は、相手側から復号した発言だけが次の会話入力です。

各端末の「理解」欄は、実際にモデルへ渡した話題／受信文と、モデルがJSONで返した公開用の短い応答方針です。内部の非公開な思考過程は表示しません。挨拶・相づちだけの返答は送信前検査で一度だけ生成し直します。

WPMは正の数値を自由入力できます。高速値を成功する速度へ自動補正しません。速すぎて復号が崩れた場合は実際の受信結果と読み取り失敗を表示します。CRC不一致の本文はLLMへ渡さず、ACKが得られなければ停止します。600 WPMでの実際の復号失敗を確認しています。

## 音と文字の経路

`tools/signal_session.mjs` がサーバー側に独立したA/Bワーカーを作り、それぞれが会話履歴・MorseAgent・受信デコーダーを持ちます。

1. 日本語は生成文の読みを辞書で得て、`WA TA SHI` のようなローマ字にします。辞書で処理できない場合はGemmaに読みを依頼します。英語は英文そのものです。
2. ヘッダー・本文・CRCを欧文モールスへ変換し、700 HzのPCM波形を生成します。
3. その波形を実時間で相手ワーカーへ渡します。相手はToneDetectorで点・線と欧文を復号します。本文を直接相手へ渡す経路はありません。
4. 日本語では受信したローマ字をかなにします。メッセージ欄の1セルが、実際の受信文字に応じて `N`、`NA`、`な` と変わります。かなへ切り替わる待ち時間は約105 msです。
5. CRC検査が通った本文だけを受信側のLLMへ渡し、次の返答を生成します。ACKも逆方向のモールス音で送ります。

Signal Flowの色は送信元に結び付けています。Aが送る本文の音はA色、Bが送る本文の音はB色です。受信側のデコーダーが検出したイベントを送信側の色として描きます。ACKも実際のモールス音なので逆側の色になりますが、その間は「受信確認を送信」「到達確認を待機」と表示し、並行して推論が終わってもACKの音が終了するまで次の送信表示へ進みません。

これは日本語をローマ字で表した**欧文モールス**です。和文符号ではありません。CRC検査後、受信したかなをWindowsの標準IMEで漢字かな交じりに整え、辞書で元の読みと照合します。標準IMEが使えない場合だけLLMの表記候補を読み合わせします。送信元の漢字を受信側へ渡す近道はありません。元のかなはタイトル属性に残し、LLMへの会話入力は実際の復号文のままです。同音異義語の選択は予測なので完全一致を保証しません。

Windowsでは[MicrosoftのIFELanguage.GetConversion](https://learn.microsoft.com/ja-jp/windows/win32/api/msime/nf-msime-ifelanguage-getconversion)を呼び出します。キーボードやクリップボードの操作、IME設定・辞書の変更、外部サービスへの送信は行いません。

高速な読みと表記変換には `fugashi==1.5.2` と `unidic-lite==1.0.8` を使用します（Python 3.12で検証）。必要なら `python -m pip install -r requirements-monitor-reading.txt` で導入し、別Python環境を使う場合は `MORSETALK_READING_PYTHON` に実行ファイルを設定します。未導入の場合はモデルによる読み・表記変換へフォールバックします。

推論欄には、実際の入力とモデルが返した「理解」「着眼点」を表示します。生成中と中断も区別します。継続会話の入力履歴は直近12メッセージ、保持履歴は約24メッセージに制限し、話題はシステムコンテキストで維持します。連番は65534で循環し、過去の全発言を無制限に保持しません。

画面の音声は、サーバーが送信したものと同じ符号・PCM生成条件で再生します。物理マイク／スピーカー間の伝送ではありません。

`monitor/inline-message.mjs` は元の本文セル方式を引き継ぐ表示部です。通信・推論・復号はこの表示部にはありません。表示のアニメーションやタブの描画が止まっても、受信文を作り替えません。停止・所有タブの切断時は、サーバーのワーカーと音声再生を終了します。

## 外部端末の監視

従来のAI Linkアプリの「デモ監視」を有効にし、監視先を `ws://127.0.0.1:18790/feed` に設定できます。Androidでは必要に応じて `adb reverse tcp:18790 tcp:18790` を使用します。外部端末のMT2/Base32経路は、この画面から開始するローマ字会話とは別方式です。外部端末を監視中は、新しい内蔵会話を開始しません。

## 検証

- `node --test tests/*.test.mjs`
- `python -m unittest discover -s tests -p test_monitor.py`
- `python tools/test_monitor_ui.py --url http://127.0.0.1:18790`
- `python tools/verify_backend_session.py --language ja --out test-results/ja`
- `python tools/verify_backend_session.py --language en --out test-results/en`
- `python tools/verify_backend_cancel.py --url ws://127.0.0.1:18790`

ブラウザ回帰試験にはPlaywrightとEdgeが必要です。実会話の検証には実Gemmaが必要です。合成イベントによるUI回帰と、実モデルによる通信検証を分けています。
